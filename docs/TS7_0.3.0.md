# TS7Play 0.3.0

Version 0.3.0 implements the approved V2 launcher interaction. The application ID
is `com.hilllaoya.ts7play`, version code is 3, and the minimum Android version is
7.1 (API 25). It embeds DiPlay from upstream commit
`615b32ce0b40cd0b99ce94ba23a512001553684f` (0.2.22).

The source-only test APK contains no runtime accessory authentication. USB and
wireless connection paths are implemented, but an independently working iPhone
connection still requires valid authentication and compatible hardware.

## Interface and setup

- The native launcher follows actual system day/night state. Its normal text
  sizes are 14, 16 and 20sp; it retains Android accessibility font scaling.
- A translucent, draggable button opens a 4-by-2 launcher. The permanent sidebar
  is removed. The old DiPlay floating bubble is disabled in this embedded build.
  The new button belongs to the current Activity and disappears outside TS7Play.
- The top strip contains connection state and time. The desktop keeps the
  CarPlay panel and two configurable app shortcuts.
- Device detection reports actual Android, display, HOME, USB, Wi-Fi and hotspot
  capabilities. It does not claim to detect or control unsupported MCU/ACC state.
- All five setup steps can be skipped. Skipped drafts do not become saved
  settings. Leaving the guide does not immediately trigger an automatic session.
- The original DiPlay operation page, connection setup and full settings remain
  available from the floating launcher.

To replace the desktop, open desktop setup and use the system default-HOME
selector to choose TS7Play. The setup screen reads back the system selection.
Keep the original vehicle launcher installed and select its recovery shortcut.
Firmware that locks the default launcher may require a manufacturer setting.

Opening the desktop at boot is controlled by the default HOME selection. The
app does not force a background Activity onto the screen. Automatic connection
is considered only when the desktop is resumed, has window focus, and meets
permission and startup-episode requirements. Manual disconnect suppresses that
episode. ACC wake behavior still requires testing on the target TS7.

## USB and Wi-Fi audit

The two desktop buttons dispatch distinct, one-shot transport requests to the
embedded DiPlay Activity. Requests are consumed while resumed and are not
replayed after recreation or a later resume.

| Route | Implementation checked | Requirements |
| --- | --- | --- |
| USB | `DiPlayActivity.connect(false)` selects wired transport; `CarPlayHostActivity.createRuntimeConfig()` reaches the controller's `startIphone()` path, USB permission, pairing, NCM and local VPN handling. | A working USB host/data port, a data cable, Android USB approval and valid runtime authentication. |
| Wi-Fi | `connect(true)` selects wireless transport and the existing Same LAN, Wi-Fi Direct or Car hotspot backend. | A compatible network/backend, Android permissions and valid runtime authentication. Same LAN does not require Internet validation. |

These are source and automated-test findings, not physical connection results.
Do not run another CarPlay receiver during a connection test. No separate DiPlay
installation is required. Existing native connection settings are preserved;
legacy TS7 LAN preferences are imported only when a native mode is not saved.

## Hotspot detection and enabling

The hotspot panel shows observed hotspot state, selected wireless mode and
control permissions. Select Car hotspot in the original connection settings,
then use the panel's detect/enable action or opt in to automatic hotspot startup.

- Startup reuses `CarHotspotTethering` and its bounded attempt, then checks the
  observed AP state. An already running hotspot is left running.
- The app does not overwrite the saved hotspot name/password. Same LAN mode
  does not turn the car hotspot on or change network topology.
- Ordinary-app startup is mainly available on Android 8-10 with the applicable
  Modify system settings permission and firmware support.
- Android 7.1 commonly needs privileged tethering access. The panel can request
  explicit authorization through the existing local ADB integration when the
  firmware already offers it; it does not open an ADB port or bypass approval.
- Permission denial, unsupported firmware, timeout and failure are reported
  separately. Observing an enabled AP does not prove DHCP or iPhone connectivity.

If the firmware blocks hotspot operation, software cannot promise to repair it.
Use a working USB data connection or a supported Same LAN network as alternatives.
